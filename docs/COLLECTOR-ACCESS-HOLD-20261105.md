# LinkedIn access hold — 5 November 2026

A scheduled run on 4 November received an HTTP 200 LinkedIn sign-up/security-verification page. The collector saved the response privately as access evidence and suspended `linkedin-public`. Later runs restored and sealed encrypted state but stopped collection with `COMPLETE_WITH_SOURCE_HOLDS`. The verified state contained 153 new records when inspected; their content remains private and is not automatically part of the 279-post assessed sample.

The collector now checks the existing source hold before opening a transport. When all enabled LinkedIn discovery consumers are held, it also skips the Exa discovery call. The report records `source_access_hold` and the safe reason `challenge_page`; it does not log the response body or source URL. Independent permitted sources can continue. Existing 401/403/429/999, challenge, quota, storage and encrypted-state safeguards remain in force. A saved-state local replay verified no discovery or source fetch while held. Scheduled runs still fail visibly while the hold persists; this change does not fabricate successful collection or silently clear the hold.

For authorized organization pages, [LinkedIn's Posts API documentation](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/posts-api?view=li-lms-2026-09) describes the `r_organization_social` permission and required Page roles. The present app does not have the reported post-read grants. Restricted member access is separately controlled by LinkedIn. Approved organization access is scoped and does not grant universal competitor or trending-post search. The app owner can review the available products and request applicable access in the [LinkedIn developer portal](https://www.linkedin.com/developers/apps); approval is not guaranteed. Never bypass a verification screen, import cookies, change source identity, or clear the hold without a source-backed authorized recovery.

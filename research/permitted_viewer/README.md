# Local source-separated research viewer

This standalone viewer reads an explicitly selected JSON file in browser memory. It does not connect to LinkedIn or any other data service and does not alter the old viewer or the research corpus. Serve the repository locally, for example `python3 -m http.server 6077 --bind 127.0.0.1`, open `http://127.0.0.1:6077/research/permitted_viewer/`, and select a snapshot with the file control. `fixture.json` contains invented examples only. Refresh to clear memory. The page has no server-side upload handler; do not put private snapshots under a publicly served directory. Source links open only when clicked. The browser's Content Security Policy blocks network connections from the page; use a current browser.

## Snapshot contract

Root object: `schema` must be `outspoken-research-viewer/1`, `generated_at` is an ISO timestamp with timezone, `operations` is an object, and `authorized_posts`, `reference_candidates`, `external_signals`, and `target_companies` are arrays of objects. Each array has a 10,000 item limit; file limit is 5 MiB. Missing optional fields are shown as Unknown. Do not include unapproved source content merely to populate this view. Fields not described below are ignored by the display. Lists must remain separated; do not put external discovery in `authorized_posts`.

- `operations`: `linkedin_status`, `status_notes`, `duplicates`, `missed_or_delayed_runs`, `daily_progress` with `new_unique_posts`, `distinct_observed_accounts`, `goals` containing the same fields (or `post_goal` / `account_goal`), plus `sources` with `source_id`, `status`, `attempted_requests`, `successful_requests`, `hold`, `quota_used`, `quota_limit`, and `observed_at`. Derive daily values on Europe/Sofia calendar boundaries upstream; unknown is not zero.
- All items: `title` or `name`, `source_id`, `source_url`, `permission_state`, `review_status`. Source URLs must be HTTP(S), with no embedded credentials. Use an explicit permission state and the correct provenance.
- Authorized posts: `author` (string or object with `name`) or `organization`, `published_at`, `publication_date_status`, `observed_at` or `collected_at`, `metrics` containing distinct `reactions`, `comments`, `reposts`, `impressions`. Each optional `snapshots` entry has `source_id`, `parser_version`, `observed_at`, and `metrics`. Counts may be nonnegative integers or `{ "status": "observed", "value": 3 }`; anything else is unknown. `trend_status`, `trend_review_status`, `trend_reason` are optional review fields.
- Reference candidates: `topic`, `author_fit`, `discovered_at`, `relevance_reason`, `performance_evidence`. Search snippets and search rank are not LinkedIn engagement evidence.
- External signals: `topic`, `source_type`, `discovered_at` or `collected_at`, `description`, and `metrics.score` / `metrics.comments`, both for the external source only.
- Target companies: `description`, `country`, `employee_count`, `funding`, `fit_status`, `content_opportunity`, `expressed_need`, `buying_interest`, `discovered_at`. Do not equate an inferred opportunity with intent.

A trend display requires a source-verified publication timestamp and two compatible, nonfuture observations at least six hours apart, from the same source and parser, with a comparable observed counter increasing and no comparable counter decreasing. These conditions describe measured change, not proof of a trend. The word Trending additionally requires upstream explicit `trend_status: "trending"` and `trend_review_status: "reviewed"`. The interface reports both observation times and counts. It does not autonomously classify trends or validate owner consent, licensing, or review.

Run `python3 -m unittest research.tests.test_permitted_viewer` for fixture, input validation, missing data, security and observation-boundary checks. The JavaScript tests require Node.js; skips are reported when it is unavailable.
